# 设计说明

这份文档记录客户端里几个重要设计的“为什么”。字段格式以 [ruleset-spec](ruleset-spec.md) 为准。

## 2D 游戏运行时（`runtime: game`）

### 目标

让故事包能做出大多数 2D 引擎级游戏（横版动作、平台跳跃、俯视角射击/冒险、弹幕、解谜），同时守住三条底线：

1. **AI 必须有**：每个故事都由 AI 参与（最高原则）。游戏也一样，只是 AI 不进实时循环。
2. **沙箱不放松**：故事来自陌生作者，不能联网、拿不到 Key/存档/文件/客户端命令。
3. **客户端外框永远可用**：按住 Esc 1 秒、安卓返回手势、右上角“⋯”都能打开暂停菜单。

### 分层

```
故事包 game/main.html + main.js + 素材（files）
        │  window.oasis.game（运行时 API）
        ▼
游戏运行时 apps/desktop/game-runtime/   ← 打包成一段 IIFE 脚本，按需注入
  loop.ts   固定步长循环、顿帧、暂停
  input.ts  输入码 → 动作（键盘/手柄/触屏），可改键
  fsm.ts    JSON 动画状态机（安全的条件表达式，不执行代码）
  index.ts  Game：素材、PixiJS 渲染、Rapier 物理、实体、镜头、粒子、九宫格 UI、场景、AI 辅助
        │  window.oasis（oasis-ui/1 桥接，postMessage）
        ▼
客户端 custom-ui.ts / play.ts：沙箱 iframe、动作校验、AI 接入点、暂停菜单
```

- `loop.ts`、`input.ts`、`fsm.ts` 是纯逻辑，不碰 DOM 和 PixiJS，单测直接跑（`apps/desktop/test/game-*.test.ts`）。
- 运行时由 esbuild 打成一个字符串，经 Vite 虚拟模块 `virtual:oasis-game-runtime` 懒加载：只有组件写了 `runtime: game` 时才下载、才注入，普通故事不受影响。
- 组件要用的素材通过 `files` 字段声明，客户端读成 `data:` 地址放进 `window.oasis.files`。沙箱里 `default-src 'none'`，素材只能这样进来。

### 为什么选 PixiJS + Rapier

- **PixiJS 8**：成熟的 WebGL 2D 渲染器，精灵批处理、九宫格、文字、滤镜都现成。它的着色器生成默认用 `new Function`，我们用 `pixi.js/unsafe-eval` 入口（预生成的同步函数），打包时再把残留的 `new Function(` 换成一个直接报错的函数，保证 CSP 测试（`csp-no-eval.test.ts`）通过、不需要 `'unsafe-eval'`。
- **Rapier 2D（compat 版）**：Rust 写的物理引擎，wasm 内嵌在 JS 里（不需要额外请求文件，适合 `data:`/内联环境）。角色控制器、传感器、碰撞事件、射线和形状查询都有。为了编译 wasm，组件文档 CSP 增加 `'wasm-unsafe-eval'`——它只允许 WebAssembly 编译，不允许 `eval`。Tauri 侧 `oasisui:` 协议的 CSP 同步更新。
- 两者都随客户端打包（约 2.4 MB），**不走 CDN**：沙箱本来就不能联网，而且离线、国内网络都要能玩。

### 循环与时间

- 固定步长（默认 60 Hz）跑逻辑和物理，渲染每帧一次；单帧最多补 5 步，卡太久就丢掉积压，避免“死亡螺旋”。
- 顿帧（hit stop）只冻结逻辑，镜头震动和渲染照常，这是动作游戏打击感的关键。
- 输入在每个固定步开始时取一次快照；两步之间“按下又松开”的点按会被锁存，不会丢。

### 输入

- 所有设备先变成“输入码”（`KeyJ`、`Pad0`、`PadAxis0-`、虚拟按键名），再按映射变成“动作”。游戏逻辑只认动作，所以改键、手柄、触屏都不用改游戏代码。
- 虚拟按键**默认不显示**，作者写了 `input.touch` 才在触屏设备上出现；不提供摇杆。这和客户端“电脑默认隐藏虚拟摇杆”的方针一致。
- 沙箱 iframe 里 Gamepad API 不一定可用（也拿不到焦点），所以客户端轮询手柄、把状态转发给组件；运行时优先用转发数据。
- Esc 由运行时转发给客户端，保证“按住 Esc 1 秒打开暂停菜单”在游戏里依然有效，短按仍可当游戏按键。

### AI 为什么不进实时循环

模型回复要几百毫秒到几十秒，还可能失败。如果每帧等 AI，游戏会卡死；如果让 AI 直接改游戏状态，又绕过了动作校验。所以：

- 游戏里的 AI 都是异步请求：`game.ai.ask()` 发组件事件 → 触发 AI 接入点 → 结果写进 `state:<key>` → 游戏读到后显示；`game.ai.action()` 调动作，由动作触发接入点。
- 请求前先等客户端空闲（AI 处理中时客户端会丢弃组件的动作和事件），拿不到就用 `fallback`，游戏照常继续。
- 适合 AI 的位置：开场/波次之间的旁白、侦察短句、NPC 台词、关卡主题、结局文字。不适合：每帧决策、碰撞判定。

### 已知限制

- 只有 2D；没有 3D、自定义着色器（GLSL）和网络对战。
- 运行时约 2.4 MB，首次打开游戏组件时加载；游戏组件（含素材）≤ 24 MB。
- 改键不会自动保存（沙箱里没有 `localStorage`），需要的话通过动作写进状态。
- 手柄依赖客户端转发；转发只在游戏组件存在时进行。
- 物理是确定性的，但游戏逻辑在组件里跑，不进存档：读档会回到故事状态（比如第几波），关卡内的实时进度不保存。
